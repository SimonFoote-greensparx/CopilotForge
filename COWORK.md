# COWORK.md - operating instructions for maintainers

This file is the primary operating instruction for anyone, human or AI, who maintains CopilotForge, and is written so
that Microsoft Copilot Cowork can carry out a bounded maintenance task by following it (design brief section 12). Read
it fully before changing anything.

## 1. Purpose

CopilotForge models the organisation needed to transform a business with Microsoft AI, as installable skills,
programmes and templates. The governing specification is the *CopilotForge detailed design brief* (29 October 2026).
Decisions that refine or depart from it are recorded in [DECISIONS.md](DECISIONS.md).

## 2. This repository and nothing else

- The only home of CopilotForge source is `https://github.com/SimonFoote-greensparx/CopilotForge`.
- CopilotForge is a **separate project** from D365Forge. Never commit to, branch, open pull requests in or otherwise
  change the D365Forge repository or website, and never copy D365Forge files into this repository. D365Forge may be
  read for reference only. `scripts/check-separation.py` fails if a file here points installs or publishing at D365Forge,
  or reuses a D365Forge skill or plugin name.
- CopilotForge is maintained with its own Cowork maintainer skills (`copilotforge-repo-publisher`,
  `copilotforge-skill-author`, `copilotforge-department-scaffolder`). Do not use the D365Forge maintainer skills here.

## 3. Repository map

See the table in [README.md](README.md#repository-map) and the system description in [ARCHITECTURE.md](ARCHITECTURE.md).

## 4. Architecture constraints

1. Departments are the reusable implementation units; programmes orchestrate them and never duplicate practitioner content.
2. `catalogue/departments.toml` is the single source of truth for department metadata. A department is `active` only when it has a folder, skills and trigger tests.
3. Skill names are unique across CopilotForge and must not reuse a D365Forge name; plugin names are `copilotforge-<department>`.
4. Reviewer-class departments (`security-privacy`, `responsible-ai`, `evaluation-quality`, `design-authority`) live in `reviewers/`. Their gates are `blocking: true` and `skippable: false` in every programme.
5. Edition and archetype overlays change depth and emphasis through `programmes/*/programme.yaml` and `data/tailoring-rules.yaml`; they never fork a skill.
6. Volatile product facts (availability, licensing, limits, preview status, names) live in `sources/*.toml` and are cited, never asserted in skill prose.

## 5. Source rules

Follow [SOURCES.md](SOURCES.md). Prefer Microsoft Learn and other primary authorities; record a reason for any
secondary source; summarise `cite-only` sources in your own words; update `last_reviewed` only after actually reviewing.

## 6. Generated-file policy

Never hand-edit a generated file. They carry a "Generated by scripts/..." header and the checks fail if they drift:
department `README.md` and `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, every skill's `references/`
folder, `catalogue/catalogue.json`, `docs/CATALOGUE.md`, the generated blocks in `README.md`, `ROADMAP.md` and
`SOURCES.md`, `cowork/README.md`, `cowork/plugins/*.zip`, the website pages `site/*.html` and `evaluations/golden/*.plan.yaml` (regenerated only with
`python3 scripts/check-profiles.py --update` after a reviewed change).

## 7. The task contract

Every maintenance task, whoever performs it:

1. Names its **allowed write surfaces** before starting (for a department: `departments/<id>/**` or `reviewers/<id>/**`,
   `tests/triggers/<id>.toml`, and any named templates). Nothing outside them changes.
2. States the **source records and decisions** it relies on.
3. Produces **explicit outputs** with acceptance criteria.
4. Ends by running `bash scripts/build-all.sh` (Python 3.11+ and PyYAML). A failed check is diagnosed and fixed in the same task where possible.
5. Produces generated artefacts **only** through repository scripts.
6. Records any change to architecture or conventions as a new or updated entry in [DECISIONS.md](DECISIONS.md).
7. Introduces **no client, employer or confidential material**. Real organisation profiles and packs stay in the
   git-ignored `input/` and `output/` folders or the user's own storage. Samples are fictional and say so.

## 8. Checks

`bash scripts/check-all.sh` runs every check CI runs (the workflow calls the same file):

| Check family | Script |
|---|---|
| Structure | `validate-skills.py`, `check-refs.py` |
| Routing | `check-triggers.py` |
| Sources | `check-sources.py` |
| Orchestration | `check-programmes.py` |
| Profiles, golden outputs, acceptance | `check-profiles.py` |
| Content | `check-templates.py`, `check-uk-english.py` |
| Safety | `check-safety.py` |
| Separation from D365Forge | `check-separation.py` |
| Generation | every `build-*.py --check` |
| Website | `check-programme-builder.py`, `build-hosting.py` (builds the full site and checks every link) |

## 9. Review gates for changes

- New or rewritten skills are `status: draft`. Only Simon Foote moves a skill to `reviewed` or `stable`.
- A change to a reviewer-class skill, a programme gate or `data/tailoring-rules.yaml` needs an explicit note in the commit
  message of what behaviour changed. Golden-plan differences must be reviewed before `--update`.

## 10. Release process

Decision D4: changes are committed directly to `main` by the maintainer while the project is in early phases. Before
committing, run `bash scripts/build-all.sh` and commit only when it passes. Releases are tagged `vMAJOR.MINOR.PATCH`
once phase 7 criteria in [ROADMAP.md](ROADMAP.md) are met.
